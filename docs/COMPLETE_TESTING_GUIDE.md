## 1. What AFTERMATH is (plain language)

Teams test code before release, but some failures only show up under real-world stress: a payment is retried because a
response was lost, two checkout workers handle the same order at once, and the customer is charged twice.
AFTERMATH is a **release rehearsal tool**: it replays a failure against a "vulnerable" release and a "repaired" release,
shows the difference, traces the cause, proposes a fix, proves the fix with tests, and holds the release until a human signs off.

### The bug being demonstrated
- File: `services/payment_worker/processor.py` (the **vulnerable** payment processor). When the same payment arrives twice
  (a client retry, or two workers at once) it checks "have I charged this idempotency key yet?" and, because the check and the
  write are not atomic and there is a simulated network delay between them, **both attempts pass the check and both charge the customer**.
- *Idempotency key* = a unique id per purchase. The rule (invariant **INV-PAY-001**, "Exactly-One-Charge-Per-Purchase") says
  one key must produce at most one charge.
- The **repaired** version holds a lock and an "in-flight" reservation per key, so a second attempt waits and then returns the
  first result instead of charging again.

### Known inconsistencies you may be asked about
- The seeded Time Machine run (27 violations, $1,240) and the Release Control matrix (12 duplicates, $1,500 total; the lost-response row is 4 / $480) are **different data sources** and do not agree. The UI labels each source.
- A live run reports **identical P95 latency (58 ms) for both variants**, so the "P95 Latency Reduction" card shows `0ms` / `1.0x faster`. That is what the simulation produces; do not present it as a latency win.
- `README.md` says AFTERMATH runs "real GitLab Duo agents". The code does not do that. Do not repeat the sentence.
- Money amounts are **simulated test amounts**, never real customer losses.

## 2. Start everything from zero (Windows PowerShell)

### 2.0 Ports and safety rules
- Frontend `3010`, backend `8010` (the repo defaults 3000/8000 are used by another project, UTTER, on this machine — leave them alone).
- The development database is `backend\aftermath.db`. **These instructions never write to it.** The demo uses its own file, `backend\aftermath_demo.db` (git-ignored, created on first start).
- Never run `Stop-Process` against a port you have not identified. Use the check below.

### 2.1 Open the project and check tools
```powershell
Set-Location E:\Projects\AFTERMATH
python --version          # expect 3.11.x   (verified: 3.11.9)
node --version            # expect 18+      (verified: v24.12.0)
npm --version
Test-Path .\backend\.venv\Scripts\python.exe     # expect True
.\backend\.venv\Scripts\python.exe -c "import fastapi, uvicorn, sqlalchemy, pytest; print('backend deps OK')"
Test-Path .\node_modules                          # expect True
```
If the venv is missing: `python -m venv backend\.venv; backend\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt`.
If `node_modules` is missing: `npm ci`.

### 2.2 Check the ports (read-only)
```powershell
foreach ($p in 3010,8010) {
  Get-NetTCPConnection -State Listen -LocalPort $p -ErrorAction SilentlyContinue | ForEach-Object {
    $c = (Get-CimInstance Win32_Process -Filter "ProcessId=$($_.OwningProcess)").CommandLine
    "{0}  PID {1}  {2}" -f $p, $_.OwningProcess, $c
  }
}
```
Nothing printed = free. If an **old AFTERMATH** process from an earlier session appears (`next start --port 3010`, or `uvicorn app.main:app --port 8010`), stop only that PID: `Stop-Process -Id <PID>`. If anything else owns the port, use other ports (e.g. 3011/8011) and change them in every command below.
(An old backend on 8010 predates the write-access guard and points at the dev database — stop it so the demo backend can take the port.)

### 2.3 Start the backend (terminal 1)
```powershell
Set-Location E:\Projects\AFTERMATH\backend
$env:DATABASE_URL = "sqlite+aiosqlite:///E:/Projects/AFTERMATH/backend/aftermath_demo.db"
$env:CORS_ORIGINS = '["http://localhost:3010","http://127.0.0.1:3010"]'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8010
```
On first start the app creates the tables (no Alembic needed locally) and seeds demo data **only if the database is empty**. Log lines to expect: `Initializing AFTERMATH database schema…`, `Deterministic seed fixtures successfully loaded.`, `Uvicorn running on http://127.0.0.1:8010`.
A fresh seeded database contains (verified): 2 releases (`rel-2026-001`, `rel-2026-002`), remediation workflow `rem-wf-001` in `PATCH_PROPOSED / PENDING`, 4 release gates (3 approved, the human gate pending), 2 agent fixtures, and the seeded experiment pair.

### 2.4 Start the frontend (terminal 2)
The API address is baked in at build time, so set it before building.
```powershell
Set-Location E:\Projects\AFTERMATH
$env:NEXT_PUBLIC_API_URL = "http://localhost:8010"
npm run build                       # ~1–2 min; must end with "Compiled successfully"
npx next start --port 3010
```
(Quicker to iterate, slower first page loads: `npx next dev --port 3010` with the same env var. For a recording use `build` + `start`.)

### 2.5 Health checks (terminal 3)
```powershell
Invoke-RestMethod http://localhost:8010/healthz                 # status: ok
(Invoke-RestMethod http://localhost:8010/api/v1/overview).releases.id    # rel-2026-001, rel-2026-002
(Invoke-WebRequest http://localhost:3010 -UseBasicParsing).StatusCode    # 200
```
Then open **http://localhost:3010**. The Overview must show `$1,500` and a two-row release registry. If it shows "Unable to Connect to AFTERMATH Engine", see §7.

### 2.6 Stop and restart safely
- Stop: press `Ctrl+C` in terminal 1 and terminal 2.
- Restart with the same commands. **Restarting does not reset data**: `aftermath_demo.db` persists approvals, experiments, and gate sign-offs.
- To get a clean demo state, close both processes and rename the file (this is a deliberate reset — do it only with your approval):
  `Rename-Item E:\Projects\AFTERMATH\backend\aftermath_demo.db aftermath_demo.used-$(Get-Date -f yyyyMMdd-HHmm).db` — the next start re-seeds a fresh one. Nothing is deleted.

### 2.7 Write-access boundary (what to expect)
POST/PUT/PATCH/DELETE requests are accepted only from the local machine (no `X-Forwarded-For`, and any browser `Origin` must be in `CORS_ORIGINS`). Reads are open. If you set `WRITE_API_KEY`, every write must send `X-API-Key`. This is a write gate, **not** user authentication; do not expose the API publicly.

## 6. Known limitations (say them plainly if asked)
1. The experiment engine is a deterministic simulation of the bug, not an execution of the real payment code; only the sandbox step runs real code.
2. The repair is a canned reference patch, not AI-generated.
3. Causal graph, blast radius, the scenario matrix and the release recommendation are static fixtures.
4. Release Control's headline text and 98.4% confidence do not react to your approvals.
5. "Trigger Benchmark Flow" creates a canned session record; "Reject Patch" rejects immediately with a fixed reason and cannot be undone for that workflow (use Trigger New Fix Workflow to continue).
6. No user authentication; the write gate is loopback-only (or `X-API-Key`).
7. Two CI jobs are placeholders (see §1).
8. No live GitLab Duo integration from the app; the Duo evidence is the separate GitLab-side flow run (unverified here).
9. The `backend\aftermath.db` development database contains leftovers from earlier test sessions (an already-approved workflow `rem-6086783d7b`, extra experiments); that is why the demo uses a fresh database.

## 7. Troubleshooting and recovery

| Symptom | Check | Fix (does it reset data?) |
|---|---|---|
| Backend does not start | `Address already in use` → run §2.2 and pick a free port; `ModuleNotFoundError` → you used the wrong Python, use `backend\.venv\Scripts\python.exe` | No data change |
| `database is locked` | two backends on one DB file | stop the extra backend; no data loss |
| Frontend says "Unable to Connect to AFTERMATH Engine" | `Invoke-RestMethod http://localhost:8010/healthz`; browser DevTools → Network: is the request going to the port you built with? | The API URL is baked at build: re-run §2.4 with the right `NEXT_PUBLIC_API_URL`. CORS error ⇒ `CORS_ORIGINS` must contain the exact frontend origin. No data change |
| Pages load but empty / "No release" | `(Invoke-RestMethod http://localhost:8010/api/v1/overview).releases` empty | The DB is not seeded (wrong `DATABASE_URL`?). Restart the backend with the §2.3 variables set; seeding runs automatically on an empty DB |
| Simulation numbers differ from this guide | scenario or seed differs | Defaults are scenario "Lost Response", Workers 5, Retries 2x, seed 42. Same inputs ⇒ same numbers |
| Time Machine still shows the seeded 27 violations | you have not executed the pair, or the run failed | Click **Execute Experiment Pair**; read the red error line under the status strip |
| A pytest test fails | run only that test with `-x -v` | note: tests use an in-memory DB, never your data |
| Remediation sandbox: "Not run" / validation fails | Windows only: sandbox uses `backend\.venv\Scripts\python.exe` if present, else the current Python; that interpreter needs `pytest` | `backend\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt` |
| "Execute Sandbox Verification" does nothing | the workflow is no longer `PATCH_PROPOSED` (already verified) — it opens the Sandbox tab with the recorded run instead | click **Trigger New Fix Workflow** for a fresh one |
| Human approval rejected (400) | workflow not `AWAITING_APPROVAL` (verify first) or already decided | run verification; or trigger a new workflow |
| Approval rejected (422) | name < 2 chars or malformed email | fix the form fields |
| Write request returns 403 | request from non-loopback host, proxy header, or foreign Origin | use `localhost` in the browser; do not put a proxy in front |
| GitLab Duo evidence unavailable | no session URL | do not claim it; show the pipeline and `Agent Activity` "Not connected" honestly |
| Want to undo a demo approval | no UI undo | switch to a fresh DB file (§2.6) |
