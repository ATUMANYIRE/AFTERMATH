**Project**: AFTERMATH — The Release Time Machine  
**Audit Date**: October 20, 2026  
**Auditor**: Principal Systems Engineer & Security Architect  
**Baseline Commit**: `783e56f`

## 1. Executive Summary

Milestone 3 successfully established the Causal Graph Engine, epistemic edge classifications (`OBSERVED`, `EXPERIMENTALLY_SUPPORTED`, `INFERRED`, `UNKNOWN`), deterministic blast radius calculations, and an interactive React Flow workspace.

However, an unsparing engineering audit of the codebase reveals critical limitations that must be addressed in Milestone 4:
1. **Source Code vs In-Code Variants**: The consequence engine currently evaluates release variants through internal branching (`if variant == 'repaired':`) rather than by compiling or executing an arbitrary patched source file.
2. **"Duo Verified" Labeling**: The UI and documentation used the phrase "Duo Verified" for repaired runs. While the GitLab Duo Agent contracts were correctly authored (`.gitlab/duo/*.yaml`), no live GitLab Duo SaaS session has executed because remote authentication remains blocked. All verification was executed by AFTERMATH's local deterministic Python engine.
3. **Telemetry & Pool Metrics**: Database connection pool saturation figures (`100/100`) were modeled by the discrete-time synthetic engine, not sampled from live PostgreSQL `pg_stat_activity` kernel sockets.

This document establishes the exact factual baseline and defines the architectural boundaries for Milestone 4: **Autonomous Remediation & Fix Verification**.

## 2. Detailed Technical Audit Findings

### 2.1 Causal Graph Provenance: Seeded Topology vs Dynamic Blast Radius
- **Current State**: `backend/app/services/causal_engine.py` maintains a persistent directed topology of 11 nodes and 8 edges in `causal_nodes` and `causal_edges`.
- **Finding**: The graph nodes and edges representing commit `a8f9c21b` are seeded deterministically in `ensure_baseline_graph` to model the known checkout fan-out race condition. However, the **blast radius metrics** (`affected_transaction_count`, `financial_exposure_usd`) are dynamically derived from live experiment runs when an `experiment_id` is passed.
- **Milestone 4 Requirement**: The causal graph must remain explicitly tied to actual experiment evidence, and remediation candidates must carry verified patch hashes and worktree execution artifacts.

### 2.2 Financial Exposure: Measured vs Seeded
- **Current State**:
  - Unexecuted release baseline (`rel-2026-001`): Displays seeded demonstration value of `$1,500.00` (or `$1,240.00` in initial M1 fixture).
  - Executed counterfactual runs: When `POST /api/v1/experiments/run-pair` executes, the financial exposure is **genuinely measured** by summing actual transactions recorded in the `synthetic_transactions` table where `status = 'RACE_CORRUPTED'` (10 orders $\times$ $75.00 avg $\times$ 2 excess debits = `$1,500.00`).
- **Correction**: The UI and API must explicitly distinguish between `SEEDED_BENCHMARK_PROJECTION` and `EMPIRICALLY_MEASURED_RUN`.

### 2.3 PostgreSQL Pool Saturation Metrics
- **Current State**: `ExperimentEvent` logs list `"Database connection pool saturated (100/100 active connections)"` and graph nodes list `100% pool utilization`.
- **Finding**: These metrics are generated by the synthetic simulation model to illustrate downstream cascade effects. They are not scraped from a live PostgreSQL metrics exporter.
- **Correction**: Labeled honestly as `SYNTHETIC_PROXY_METRIC`.

### 2.4 "Duo Verified" vs Local Verification
- **Current State**: Several UI badges read `"Repaired Release (Duo Verified)"`.
- **Finding**: GitLab remote authentication (`atumanyire-labs/aftermath`) is blocked. No live Duo Agent execution has occurred on GitLab.com. The repair was verified entirely by the local Python Consequence Engine and Pytest test suite.
- **Correction**: Replace misleading "Duo Verified" text with `"Engine Verified (Duo Contract Prepared)"` or `"Local Consequence Sandbox Verified"`. Reserve "Duo Verified" strictly for live GitLab Duo Agent execution records.

### 2.5 Payment Idempotency & Crash Recovery
- **Current State**: `IdempotencyRecord` enforces a durable database uniqueness constraint `(experiment_id, scope, idempotency_key)` with status transitions `IN_FLIGHT -> SETTLED`.
- **Finding**: Under concurrent requests, duplicate database insertions are rejected by the SQLite/PostgreSQL storage engine. However, if a worker crashes while a record is in `IN_FLIGHT` state, the lease expires after 30 seconds (`lease_expires_at`), but an active lease reclamation background worker was not implemented.
- **Milestone 4 Action**: Explicitly verify lease expiration and crash recovery in the test suite.

### 2.6 Patch Execution Capability
- **Current State**: The existing experiment runner selects behavior based on `variant == 'vulnerable'` or `variant == 'repaired'`.
- **Critical Gap**: It cannot ingest an arbitrary `.diff` patch file, apply it to real source files in an isolated temporary Git worktree, execute the patched code in an isolated subprocess/sandbox, and measure the real consequence delta.
- **Milestone 4 Primary Objective**: Build a genuine Patch Engine and Worktree Runner that applies unified diffs to real source files and executes tests directly against the patched code.

## 3. Milestone 4 Architectural Objectives

1. **Persistent Remediation State Machine**:
   `DETECTED -> INVESTIGATING -> PATCH_PROPOSED -> VALIDATING -> AWAITING_APPROVAL -> APPROVED / REJECTED -> COMPLETED` (with `FAILED`, `CANCELLED`, `BLOCKED`).
2. **Real Source Target & Patch Generator**:
   Create a dedicated real source service `services/payment_worker/processor.py`. The Remediation Engineer must read this file, diagnose the race condition, generate a unified diff, and apply it to an isolated worktree.
3. **Execution-Backed Validation**:
   Run the exact failing test suite and consequence scenario against the patched worktree code. If the patched code fails or is not executed, the repair must be marked `UNVERIFIED` or `FAILED`.
4. **Human Approval Gate**:
   Interactive Repair Studio UI showing side-by-side diffs, test logs, and explicit "Approve Patch" / "Reject Patch" controls with audit persistence.
5. **Security Boundaries**:
   Allowlist file modifications to `services/payment_worker/**`. Prohibit writes to `.env`, `.git`, `backend/app/config.py`, or system paths. Reject destructive shell commands.
